# Appki MVP contract

This is the integration contract for the current implementation. All public-facing copy is Russian. Product definitions and published immutable IPA artifacts determine the catalog; Happ retains a legacy fallback, and V2RayTun or another configured product can be connected through the registry. Unpublished planned products cannot be purchased or installed. Missing credentials must produce a truthful unconfigured state, never a fake payment, code or entitlement.

## HTTP API (same-origin)

- `GET /api/config` -> `{brand, bot_username, support_url, payments_mode, payments_configured, telegram_configured}`. Do not expose secret values.
- `GET /api/apps` -> `{items: App[]}`.
- `GET /api/apps/{slug}` -> App.
- App: `{slug,title,subtitle,description,version,size_bytes,minimum_ios,price_rub:string|null,category,features:string[],available:boolean,coming_soon:boolean}`. Bundled slugs: `happ`, `v2raytun`, `sber`, `tbank`, `vtb`, `chatgpt`, `deepseek`; registry configuration can add products. Unconfigured planned products have `coming_soon:true`, `available:false`, `price_rub:null`, empty version/minimum iOS and zero size; the UI hides missing price/specifications and shows «Скоро» / «Готовим к запуску». Publishing a validated artifact connects the configured product. A connected product whose file becomes unavailable has `coming_soon:false` and is temporarily unavailable. Configured prices are decimal strings; the shop mode determines test/live payment eligibility.
- `POST /api/auth/telegram` JSON `{init_data:string}` -> `{access_token, user:{id,first_name,username?},expires_at}`. Validate Telegram HMAC + age, issue an opaque random token. All private APIs use `Authorization: Bearer ...`.
- `GET /api/me` -> `{user:{id,first_name,username?}}`.
- `POST /api/orders` JSON `{app_slugs:string[],request_id:string,expected_amount_rub?:string}` -> Order. Accepts 1–20 distinct purchasable catalog slugs; no quantities. Any planned or unavailable item, including in a mixed cart, is rejected before creating an order or calling the payment provider. Legacy `{app_slug:string,...}` remains supported; supply exactly one of `app_slug` and `app_slugs`. Slugs use `[a-z0-9-]{1,64}`; `request_id` uses `[A-Za-z0-9_-]{8,64}`. The server sums catalog prices with Decimal and saves each item's price. `expected_amount_rub`, when supplied, must be a decimal string with two fractional digits; a mismatch returns 409 before creating a payment. The current frontend always sends the confirmed cart total.
- Order creation is idempotent per user and `request_id`; repeat the same key, item set and expected total when retrying. Reusing a key with a changed selection or saved-order total returns 409. A new key reuses a single unresolved order with the same cart, total and shop mode; unresolved overlapping carts are blocked rather than creating a second payment. Known overlapping payments are checked first. A previously paid purchase permits a separate purchase with a new key; reconciliation of a pending attempt still follows the existing duplicate-payment guards. Requires configured YooKassa and available IPA files. Returns the provider confirmation URL when available; an old unknown attempt returns its saved order with `requires_payment_review`, without another provider creation.
- `POST /api/orders/{id}/retry-payment` -> Order. Owner can retry an uncertain creation with the same stored provider idempotence key; creation attempts older than 23 hours are refused. For a known pending payment, fetch its current provider state before returning a confirmation URL. Never creates a second order.
- `GET /api/orders?status=succeeded|pending|canceled|refunded` -> `{items:Order[]}` owned by current user, newest first, up to 100 matching orders. Omitting `status` retains the unfiltered list. Purchases and pending attempts are fetched separately so unpaid drafts do not displace purchased apps.
- `GET /api/orders/{id}` -> Order owned by current user. Pending payments with a provider ID may be reconciled against YooKassa, at most once per 5 seconds for ordinary sequential reads.
- `POST /api/orders/{id}/items/{slug}/install-link` -> `{url,expires_at}` for an item in an owned, paid order in the current payment mode. The installation window ends 12h after `paid_at` (legacy fallback: order `created_at`), and closes immediately after the first `installed:true`. Creates an item-scoped bearer grant with the configured TTL (at most 1h); every install-page, manifest and IPA request also checks the installation window and current item state.
  The first delivery pins the item to an immutable artifact and its activation profile. Subsequent links use that artifact; changing a published release does not switch existing delivery assignments. Artifact IDs, source-account IDs and filesystem paths are private server data, absent from the public API.
- `GET /api/orders/{id}/items/{slug}/activation` -> Activation for an installed item in an owned, paid order in the current payment mode. Activation: `{mode:'manual'|'credentials',apple_id?:string,password?:string,instructions:string,support_url:string,server_now:ISO,activation_expires_at:ISO,can_request_code:boolean,code_request:CodeRequest}`. The window ends 6h after the first installation mark. GET does not start or extend it. Access before installation returns 409, after expiry 410, after completion 409; credentials and code requests are closed on completion. Never log activation contents. The current source of codes is manual support; no automatic collector or fabricated code is exposed.
- `POST /api/orders/{id}/items/{slug}/activation/code-request` without a body -> `{server_now:ISO,activation_expires_at:ISO,can_request_code:boolean,code_request:CodeRequest}`. Creates manual-support request metadata only; it does not contact support automatically, request an Apple SMS or generate a code. The user contacts support through `support_url`. The same installation/window/completion checks apply. Repeating within 60 seconds returns 200 with the same request ID; a later request creates a new metadata row without extending the activation window.
- `CodeRequest`: `{id:string|null,status:'not_requested'|'manual_required',requested_at:ISO|null,retry_at:ISO|null,retry_after:number,expires_at:ISO}`. `retry_after` is the remaining service cooldown in seconds. `expires_at` is the end of this item's 6h activation window, not the validity of an Apple verification code. No code value is included. Metadata lives in `activation_code_requests`, linked to the order item; an operator data reset must delete these rows before deleting their order items.
- Legacy `POST /api/orders/{id}/install-link`, `GET /api/orders/{id}/activation` and `POST /api/orders/{id}/activation/code-request` remain available for single-item orders. Multi-item orders must specify an item; otherwise 409.
- `PATCH /api/orders/{id}/items/{slug}/state` JSON `{installed?:boolean,activated?:boolean}` -> OrderItem. Requires ownership and a paid order in the current mode. At least one non-null strict boolean is required; any `false` value is rejected with 409. The first `installed:true` within the installation window saves its timestamp, revokes all OTA grants for the item and starts its 6h activation window. `activated:true` requires an installation mark or `installed:true` in the same request, and a current activation window; it completes access. True marks are idempotent and preserve their first timestamps. There is no customer reset or reinstallation path. These are user-reported steps, not physical installation checks, Apple confirmation or automated 2FA delivery.
- `POST /api/payments/yookassa/webhook`: verify event by fetching payment from YooKassa, check payment ID, amount, RUB currency, merchant recipient if provided, order metadata, test flag, succeeded+paid status; perform idempotent state update. Respond 200 to safely ignored duplicates/unrelated events, 503 on provider outage for retry.
- `GET /healthz` -> minimal health; no keys, paths, or personal data.
- errors JSON `{detail:string}` (prefer user-understandable Russian).

Order: `{id,app_slug,app_title,amount_rub,total_rub,items:OrderItem[],currency:'RUB',status:'pending'|'succeeded'|'canceled'|'refunded',payment_url:string|null,has_payment:boolean,can_retry_payment:boolean,requires_payment_review:boolean,created_at,paid_at:string|null,test:boolean,can_install:boolean}`.

`payment_url` is exposed only for a pending payment. `has_payment` means a provider ID is known. `can_retry_payment` permits recovery of an unknown creation in the current shop mode within the 23-hour retry window. An older unknown attempt has `requires_payment_review`; retain it for provider/webhook reconciliation, do not cancel it or create a replacement based on elapsed time. New browser request keys must not bypass an unresolved overlapping purchase.

OrderItem: `{app_slug,app_title,amount_rub,installed:boolean,activated:boolean,installed_at:ISO|null,activated_at:ISO|null,server_now:ISO,install_expires_at:ISO|null,activation_expires_at:ISO|null,can_install:boolean,can_activate:boolean,can_request_code:boolean,access_status:'install'|'activate'|'completed'|'install_expired'|'activation_expired'|'unavailable'}`. Money values are decimal strings; timestamps are ISO strings. `amount_rub` and `total_rub` are the same saved order total. Top-level `app_slug` (first sorted item) and `app_title` (combined titles) remain for compatibility; use `items` for individual purchases. Order `can_install` is true when at least one item can be installed. The server derives eligibility from verified payment, current test/live mode, artifact availability, immutable state marks and the applicable window. Repeated purchases of one slug remain separate order items with separate deadlines; identify them by `(order_id, app_slug)` and never collapse My Apps by slug alone.

The 12h installation window, 6h activation window and 60-second request cooldown are Appki service policy. Apple's checked [verification-code instructions](https://support.apple.com/en-us/102606) and [Mac guide](https://support.apple.com/guide/mac-help/mchl8bd4e9c2/mac) do not specify an exact TTL for the six-digit Apple Account code. Any future local code-display timer must be labelled as a display limit; Apple determines whether the code is accepted.

## Installation URLs

- `GET|HEAD /install/{token}` serves a standalone private installation page; the item-scoped bearer grant provides access without Telegram auth. On iPhone/iPad it attempts the `itms-services` link once automatically; the explicit install link remains available if the browser blocks the attempt. Only this page permits the exact static script via a CSP SHA-256 hash. Manifest and IPA responses retain the script-free CSP. A browser/device launch attempt never marks the app installed or activated.
- `GET|HEAD /install/{token}/manifest.plist` contains the exact IPA bundle ID/build and absolute HTTPS asset URL.
- `GET|HEAD /install/{token}/app.ipa` streams the unchanged local file, supports byte ranges, no directory access. Missing/expired/revoked grants fail; an old token also fails after installation, completion or the installation deadline. Tokens are hashed in DB. No request-path logs, analytics, external assets or referrers on these routes.
- Frontend routes: `/` (catalog/cart), `/apps/{slug}` (catalog with product details for connected and planned products), `/orders` (purchased apps only, with installation/activation), `/payment/{id}` (payment status), `/orders/{id}` (order), `/orders/{id}/apps/{slug}` (item installation/activation), `/how-it-works` (public explanation of purchase, installation and activation), `/help`, `/payment/return?order_id=...`. Private pages require a Telegram session; the return page never itself marks a payment paid. Known pending payments are reconciled quietly while the app is open; no unpaid list or checkout entry point is shown in My Apps.
- Frontend should work in Telegram native WebView and as read-only public preview in a normal browser. Do not create a demo user session in production. User-visible disabled checkout if Telegram authentication or payment config is unavailable.
- The cart is stored in browser sessionStorage per user. Checkout shows selected items and the total, requires explicit confirmation, and preserves the request key for an uncertain purchase. The server is authoritative for prices, entitlements and saved installation/activation marks.

## Ownership of implementation

- Backend agent: `backend/appki/config.py`, `db.py`, `auth.py`, `main.py`, `ota.py`, backend API/security/integration tests.
- Payments agent: `backend/appki/payments.py`, its tests. Contract below.
- Frontend agent: all `web/` files, responsive design and build.
- Root: bot, deployment, env, docs, integration, final QA.

## Payment adapter

Provide `YooKassaClient(shop_id,secret_key,mode='test',api_base='https://api.yookassa.ru/v3', client=None)` using httpx AsyncClient (client injection for tests only). Runtime must use official HTTPS API, never accept user API hosts.

`async create_payment(*, order_id:str, amount_rub:str, description:str, return_url:str, idempotence_key:str) -> dict` sends capture=true + confirmation.redirect + metadata.order_id; Basic Auth; Idempotence-Key header. Exact amounts, no floats. In live mode it additionally sends `payment_method_data: {type:'sbp'}` for [YooKassa's SBP redirect checkout](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/manual-integration/other/sbp). Test mode keeps the provider checkout without forcing SBP: YooKassa's [test shop supports cards and the YooMoney wallet](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing). The app and bot use neutral payment copy in both modes; server-side mode checks remain mandatory. Changing interface text does not enable live mode. The configured default installation price is 490.00 RUB; saved order totals remain immutable.
`async get_payment(payment_id:str) -> dict` returns authoritative provider JSON.
`async close()` releases owned client.
`PaymentConfigurationError`, `PaymentProviderError` (safe messages; no key/raw payload/URL leaks), `PaymentValidationError`.
`validate_payment(payment:dict, *, order_id:str, payment_id:str|None, amount_rub:str, shop_id:str, mode:str) -> str` returns pending/succeeded/canceled only after validating id, metadata, amount/currency, test flag and recipient account_id when supplied. succeeded requires paid=true and captured amount consistency. Throws on mismatch. Creation may have pending + paid=false.

Refunds: verified full-refund notifications mark the order refunded and revoke all its installation grants. Partial refunds retain access. No automatic money movement/refund initiation without owner operation.

## Private acquisition pipeline

The operator CLI runs as `appki-acquirer`, separate from the web service. Jobs select an application and account profile. Profiles have isolated authorisation state and a per-account interprocess lock; different accounts can execute concurrently. Credentials and passphrases never enter job payloads or subprocess arguments.

Downloaded files are validated and imported as immutable artifacts with bundle/version/hash metadata and actual source-account provenance. Downloading does not publish a product or acquire a paid App Store license. Publication is a separate operator command. Missing or expired loader authorisation pauses the job for an operator; loader 2FA is separate from customer activation.

Existing Happ purchases migrate without changing saved totals or installation marks. Legacy source-account provenance remains unknown rather than being invented. The original Happ environment settings continue to provide the fallback catalog and legacy activation. Newly imported artifacts never inherit legacy credentials implicitly.

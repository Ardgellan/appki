# Эксплуатация

## Файлы и службы

- Код: `/opt/appki/releases/<release>`, текущий `/opt/appki/current`.
- Python: `/opt/appki/venv`.
- Секреты: `/etc/appki/appki.env`, `root:appki`, режим `640`.
- SQLite и позиция бота: `/var/lib/appki`, пользователь `appki`, режим `700`.
- Оригинальный IPA: `/var/lib/appki/apps/Happ.ipa`, `root:appki`, режим `440`.
- Службы: `appki-api`, `appki-bot`; backend слушает только `127.0.0.1:18880`.
- nginx: существующий vhost `/etc/nginx/sites-available/happ-ota` переведён на новый сервис. Другие службы VPS не изменяются.
- Старый тестовый `happ-ota.service` и исходный IPA сохранены; старые истёкшие ссылки новым API не обслуживаются.

Проверка без вывода секретов:

```sh
systemctl status appki-api appki-bot --no-pager
curl -fsS https://85.239.144.214/healthz
curl -fsS https://85.239.144.214/api/config
journalctl -u appki-api -u appki-bot -n 50 --no-pager
```

У nginx и uvicorn отключены журналы URL, чтобы установочные токены не попадали в них. Тело платёжных ответов, Telegram initData и пароли не журналируются.

## Обновление .env

Предпочтительный путь: редактировать локальную `.env` и повторить `scripts/deploy.sh`. Локальные значения становятся источником настроек VPS. После изменений напрямую на VPS не запускайте старую локальную копию настроек.

Без токена Telegram служба бота отключена; это штатный режим просмотра. При непустом токене развёртывание включает обработчик. Наличие токена ещё не означает его действительность: после первого подключения проверьте журнал и отправьте `/start` боту.

## Резервные копии и откат

Перед каждым обновлением скрипт сохраняет согласованный снимок SQLite и предыдущую `.env` в `/var/backups/appki`. Это резервирование при развёртывании, не регулярная внешняя резервная копия. Перед коммерческим запуском настройте ежедневный backup на независимое хранилище и политику хранения.

Предыдущие релизы сохраняются. Если новый API не проходит healthcheck, скрипт возвращает прежнюю ссылку `current` и прежнюю `.env` (если они существовали). База автоматически назад не откатывается. Текущая схема создаётся без разрушительных миграций.

Для ручного отката выберите существующий предыдущий каталог, переключите `/opt/appki/current`, восстановите соответствующие настройки при необходимости и перезапустите службы. Не копируйте рабочий SQLite-файл обычным `cp` во время записи; используйте SQLite backup API.

## HTTPS

Текущий адрес — HTTPS по IP `85.239.144.214`. Уже существующий `happ-certbot-renew.timer` обновляет IP-сертификат через HTTP challenge `/var/lib/happ-acme`; этот маршрут сохранён. Домен можно подключить позже вместе с новым сертификатом и обновлением настроек бота.

## Активация

По умолчанию `ACTIVATION_MODE=manual`: оплаченный пользователь видит инструкцию и контакт поддержки. Смена основного iCloud не требуется. Поля `ACTIVATION_APPLE_ID` и `ACTIVATION_PASSWORD` пусты; не заполняйте их личным аккаунтом для массовой выдачи.

Если владелец отдельно выбирает режим выдачи реквизитов, оба значения нужны одновременно; API отдаёт их только владельцу оплаченного заказа. Такой режим не решает получение 2FA, блокировки Apple или права распространения.

### Доставка Apple 2FA: исследование, не действующая функция

Код подтверждает вход в аккаунт, используемый для «Контента и покупок»; он не является кодом, ограниченным одним приложением. Источник — доверенное устройство этого аккаунта либо его доверенный номер (SMS/звонок).

Рассмотрены выделенный доверенный Mac со сборщиком и собственная SIM с SMS-шлюзом. SMS рекомендован для первого эксперимента, но окончательный способ не выбран владельцем и реальная доставка не проверена. Не устанавливать сборщик на личные устройства и не менять настройки аккаунтов без отдельного согласования.

До внедрения остаётся ручная помощь. Для будущей автоматизации нужны очередь активаций, привязка к владельцу оплаченного заказа, защита от старых/повторных событий, ограничения повторных запросов, отказ при неоднозначной адресации и отсутствие кодов в логах/резервных копиях. Слепое одобрение всех уведомлений входа недопустимо.
